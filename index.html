The problem

AI coding tools don't know your software.
You pay for that on every request.

To work on your codebase, today's assistants search it and paste the results into the prompt, then do it again on the next request, and the next.

Spend scales with your codebase

Context tokens grow with repository size × engineers × requests. Agents multiply it again. The bill grows faster than the team.

Long prompts are slow prompts

Thousands of context tokens must be processed before the first word comes back. Developers feel it on every completion.

Your code keeps leaving the building

Every request ships proprietary source to someone's API. In regulated teams that blocks adoption entirely, and self-hosted models don't know your code.

How it works

Teach the model your codebase once.
Keep it current with every commit.

A hypernetwork, trained once on hundreds of repositories, reads your code and writes a small adapter for the model. No training runs on your side and no context stuffing.

01 · CONNECT

Point it at a repository

Code2LoRA reads the code and its git history locally. Encoding runs on CPU; the large model is never loaded for this step.

$ c2lt → /adapt
02 · COMPILE

Get a repository adapter

The hypernetwork writes a LoRA adapter for your repository in a single pass. No gradient steps and no per-repository training job.

<10 ms generation · 8 KB stored per repo
03 · SERVE

Use it with your model

The adapter plugs into an open-weight coding model on your GPUs or a laptop CPU. Prompts stay short; repository knowledge is already in the weights.

PEFT · GGUF / llama.cpp · 4-bit · 8-bit

Security & trust

Built for teams that can't send their code to an API

Code2LoRA was designed around open-weight models you run yourself. Nothing about it requires a network connection to us.

Fully offline

Air-gap capable. Set C2L_OFFLINE=1 and nothing calls out once models are cached.

Your hardware, your models

Adapter generation runs on CPU; serving runs on your GPUs or quantized on a laptop. No vendor in the loop.

Knowledge in weights, not prompts

Repository knowledge sits in a small adapter file you own, not in prompts copied to someone else's logs.

Isolated and revocable

One adapter per repository or client. Delete the file and that knowledge is gone from the system.

Inspectable

Published method, open checkpoints, MIT-licensed CLI. Your security team can read exactly what runs.

FAQ

Questions buyers ask us

Does any of our code leave our network?

No. Adapter generation and serving both run on your machines, and the offline mode (C2L_OFFLINE=1) blocks network access once models are cached. We never need access to your repository.

Which languages and models do you support?

Today: Python repositories with the Qwen2.5-Coder open-weight model. New languages and models are trained with design partners. Tell us your stack and we'll tell you how close it is.

Does this replace RAG?

For repository knowledge, it removes the need to paste context on every request. On our benchmark Code2LoRA beats retrieval by 16 points with zero retrieved tokens. You can still combine it with retrieval for the latest uncommitted changes.

What hardware do we need?

Adapter generation runs on CPU. The terminal works on a laptop with 8 GB of RAM using a quantized model. In production, adapters plug into your existing GPU serving, or a CPU server with enough memory.

How does it stay current as the code changes?

The Live engine keeps a compact state of your commit history. Each new commit updates the adapter incrementally instead of rebuilding it. You choose the cadence: per commit, per merge, or on a schedule.

What does a pilot look like?

Free for design partners. We set up Code2LoRA on one repository and team, you use it for a week on real work, then we review the measured token savings, latency and accuracy with you and your stakeholders.

Is it open source?

The terminal CLI is MIT-licensed, and the research checkpoints and benchmark are public on Hugging Face. Enterprise, SDK and partner deployments are commercially licensed.
